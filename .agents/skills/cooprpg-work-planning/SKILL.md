# CoopRPG 작업 계획과 판단

이 스킬은 작업을 선택하거나 계획을 검토하는 절차다. [AGENTS](../../../AGENTS.md)와 최신 사용자 요청을 먼저 확인한다. 계획 요청으로 구현·빌드·게임 시험·커밋·게시·목표 모드·에이전트 실행 권한을 얻었다고 해석하지 않는다.

## 기준과 실제 상태 읽기

1. 요청이 계획 수립, 다음 작업 선택, 계획 검토 중 무엇인지 구분한다. 실행까지 요청했다면 허용된 범위를 별도로 확인한다. 명확한 요청을 다시 승인받지 않는다.
2. 실제 Git 루트·브랜치·HEAD·미커밋/미추적 변경을 확인한다. 기본 저장소는 `C:/CoopRPG`이며 명시한 worktree도 가능하다. 저장소 밖 채팅에서는 해당 저장소의 AGENTS와 파일을 직접 읽고 적용 위치를 밝힌다. 브랜치 전환이나 기존 변경 정리를 계획의 자동 단계로 만들지 않는다.
3. [작업 판단 가이드](../../../Docs/Planning/WorkingGuide.md)를 읽고, [Project](../../../Docs/Project.md#mvp-scope), [현행 카드](../../../Docs/Roadmap.md#next-work), [실제 진행](../../../Docs/Development.md#daily), 관련 [시험](../../../Docs/Validation/Index.md#active-tests)과 필요한 코드만 대조한다. 같은 세션에서는 변경·관련 구간만 재확인한다. 가이드에 현재 진도를 복사하지 않는다.

## 판단하고 제안하기

- [선택 기준](../../../Docs/Planning/WorkingGuide.md#decision)으로 선행 조건·핵심 미검증·완주 기여·학습 필요·작업 비용을 비교한다. 다음 작업 요청에는 주 작업 하나와 이유를 먼저 제시한다. 전체 계획 요청에는 의존성·중간 목표·점검 시점을 연결하고, 근거 없는 날짜·진척률을 확정하지 않는다.
- 계획 검토에서는 유지·수정·보류할 부분을 근거와 영향으로 설명한다. 문제가 없으면 유지 이유와 한계를 보고한다. 계획만 검토했으면 코드 정확성·게임 시험 통과를 주장하지 않는다. 코드 검토나 기능 문서 편집이 주 요청이면 해당 절차를 사용한다.
- 완료·실패 조건은 채택 규칙에서 정한다. 구현의 현재 동작을 기대값으로 그대로 복제하지 않는다. 클라이언트 차단/서버 거절, PIE/독립 패키지, AI/사용자 확인을 구분하고 미확인 정보는 좁혀 확인하거나 한계로 남긴다.
- 학습·구현·빌드 대기·시험·기록을 포함한 예상과 첫 점검 시점을 제시한다. 실제 속도 근거가 없으면 추정 또는 미산정으로 표시한다. 기한 미달 시 선택지·손실을 밝히며 범위와 통과 기준을 임의 축소하지 않는다.
- 사용자의 실제 선택·학습·직접 확인과 AI 수행을 구분한다. 모든 작업에 모든 역량·사례·문서를 요구하지 않는다. 세션 분리가 필요할 때만 역할·수정 범위·공유 자원을 제안하고 실제 위임은 허용 범위를 따른다.

## 결과 전달과 연결

[가이드의 사용 양식](../../../Docs/Planning/WorkingGuide.md#usage)을 작업 크기에 맞춰 줄여 쓴다. 현재 상태/근거, 선택 이유, 포함/제외와 완료 조건, 학습/역할/점검 시점, 갱신 문서와 다음 행동을 연결한다. 새 문서나 계획 파일을 매번 만들지 않는다.

제안만 요청받으면 답변으로 전달한다. 의미 있는 결정이나 채택된 작업의 기록은 AGENTS에 따라 기존 Roadmap·Development에 반영하되 제안과 채택을 구분한다. 실행 결과의 기능 설명·도식 갱신은 [cooprpg-feature-docs](../cooprpg-feature-docs/SKILL.md)를 사용한다. 인계에는 실제 버전·dirty 상태·남은 확인을 남기고 검증 완료를 소급하지 않는다.
