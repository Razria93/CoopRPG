# CoopRPG 기능 문서 갱신

이 스킬은 기능 문서의 내용·갱신 절차를 담당한다. 실제 저장소의 [AGENTS](../../../AGENTS.md)와 최신 사용자 지시를 먼저 확인한다. 실행·커밋·게시 권한을 추가하지 않으며, 문서화만 요청받았다면 게임 코드나 시험을 실행하지 않는다.

전체 계획·다음 작업 선택·작업 계획 검토가 주 요청이면 [cooprpg-work-planning](../cooprpg-work-planning/SKILL.md)과 [작업 판단 가이드](../../../Docs/Planning/WorkingGuide.md)를 사용한다. 이 스킬은 실제 기능 설명과 기록의 갱신을 담당하며 계획 판단 기준을 중복 작성하지 않는다.

## 기존 문서부터 찾기

1. 실제 Git 루트·브랜치·HEAD·미커밋 변경과 [현행 카드](../../../Docs/Roadmap.md#next-work)를 확인한다. 다른 세션의 완료 메시지 대신 해당 코드·시험 기록을 읽는다. 작업 위치가 저장소 밖이면 저장소 경로와 적용한 AGENTS를 명시한다.
2. [문서 색인과 판본](../../../README.md#document-editions), [문서 생성·갱신 기준](../../../Docs/Development.md#feature-documents)으로 기존 주제를 찾는다. 같은 목적·책임·검증 경계면 기존 절을 보완한다. 함수·GE·작업 턴·강의 챕터가 늘었다는 이유만으로 파일을 만들지 않는다.
3. 독립된 문제·데이터 책임·검증 경계를 설명해야 할 때만 새 주제 문서를 만든다. 실제 내용이 없는 미래 기능 파일은 만들지 않는다. 구조 전체의 원본은 Architecture, 시행착오 이력은 Development, 시험 상세는 Validation에 유지하고 기능 문서에서 연결한다.

## 내용과 근거 연결

- 새 문서나 큰 절을 구성할 때 [기능 문서 양식](references/feature-document.md)을 읽는다. 작은 변경에서는 영향받는 설명·그림·코드 참조·검증 범위만 고친다. 기존 앵커와 승인된 PDF 도식의 의미를 유지한다.
- 요구/제안/구현/검증을 구분한다. 코드가 있어도 실제 시험이 없으면 검증 대기다. 기존 시험은 날짜·코드/빌드·환경·조건을 맞춘 범위에서 참조하고 새 실행으로 기록하지 않는다. 클라이언트 차단과 서버 거절, PIE와 패키지, AI 재현과 사용자 조작을 섞지 않는다.
- [역량 근거 기준](../../../Docs/Development.md#competency-evidence)에 따라 실제 결정·학습 사건만 연결한다. 사용자의 질문을 이해 완료로, AI의 제안을 사용자의 판단으로, AI의 시험을 사람의 확인으로 바꾸지 않는다. 세 역량을 매 절에 억지로 채우지 않는다.
- 의미 있는 사용자 결정·적용·직접 검증이 확인되면 원본을 먼저 갱신하고 [AI 협업 근거 색인](../../../Docs/Portfolio/AICollaborationEvidence.md)의 같은 사례 행을 보완한다. AI 자동 시험만 있는 상태와 사용자 확인 차례를 구분하며, 단순 수정에 새 사례를 강제하지 않는다.
- 사실의 원본은 코드·채택 규칙·시험 기록이다. Markdown은 유지·탐색용 설명, PDF는 편집된 검토/공유본으로 역할을 구분한다. 서로 다른 편집을 허용하되 사실이 다르면 원자료로 확인하고 양쪽의 영향받는 부분을 정정한다.
- 강의 노트는 UE5_Practice의 원본을 참조하고 프로젝트에는 적용 이유·차이·결과만 쓴다. 다른 장비나 외부 독자는 로컬 강의 경로를 열 수 없으므로 프로젝트 판단에 필요한 핵심은 문서 본문에도 설명한다. 강의 원문·비공개 멘토링 자료를 자동 게시하지 않는다.

## 작성 시점과 세션 인계

- 착수 때 기존 문서와 완료 조건을 찾고, 의미 있는 설계·동작 변경 후 해당 절을 갱신한다. 시험 후에는 실제 결과와 한계를 연결한다. PDF/HTML은 중간 목표 완료·공유 요청 때 갱신하며 매 턴 새로 출력하지 않는다.
- [세션 협업 규칙과 인계 양식](../../../Docs/Development.md#collaboration-operation)을 따른다. 같은 공유 파일은 정한 담당 한 명이 통합한다. 문서 작업은 기준 커밋 또는 미커밋 스냅샷을 고정하고, 작업 중 코드가 바뀌면 영향받는 설명을 다시 대조한다.
- 문서 판본은 README의 색인 한 곳에 등록한다. Markdown·PDF 편집 원본·출력본·기준 코드/시험·검수 범위·공개 상태를 연결한다. 로컬 산출물은 경로와 식별 정보를 적고 접근 불가능한 파일을 공개 링크처럼 표시하지 않는다.

## 외형과 종료 확인

- `common-document-style`을 사용할 수 있으면 함께 적용한다. 이 장비의 설치 경로는 `C:/Users/starb/.codex/skills/common-document-style/SKILL.md`다. 없으면 저장소 양식의 제목 계층·간결한 문단·표·분리된 근거 문단을 유지하고, 승인 HTML/PDF 외형의 재현은 미확인으로 보고한다. 스킬을 임의 설치하거나 기존 문서를 전면 재구성하지 않는다.
- 관련 문단 아래 빈 줄 뒤에 `**근거** · 링크`를 두고, 독립 문서는 필요한 경우 마지막에 `근거 및 더 읽기`를 둔다. 본문을 뒷받침하는 자료와 심화 자료를 구분한다.
- 내용·기여·코드/시험 버전과 링크·앵커를 확인한다. 공개 편집본은 해당 형식 스킬로 넓고 좁은 화면 또는 PDF 페이지를 실제 검수한다. 렌더링하지 않았다면 정적 검수와 구분한다.
- 기존 저장소 검사 `Tools/Validation/Validate-Repository.ps1`을 재사용한다. 결과를 Development에 연결하고 다음 카드가 바뀌면 Roadmap도 갱신한다. 검증을 못 한 부분을 숨기거나 문서 편집 때문에 게임을 재빌드하지 않는다. 최종 보고에는 변경·실제 확인·미확인·다음 행동을 적고 Git 작업은 AGENTS와 사용자 지시를 따른다.
