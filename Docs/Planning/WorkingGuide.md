# CoopRPG 작업 판단과 포트폴리오 운영 가이드

CoopRPG · 작성 2026-11-15 · 사람과 에이전트가 계획·다음 작업·검토에 함께 사용하는 안내.

현재 근거를 바탕으로 필요한 작업을 선택하고, 학습·구현·검증 결과가 포트폴리오 목적에 어떻게 연결되는지 판단한다. 이 문서는 판단 방법과 이유를 설명한다. 게임 규칙·현재 진척·실행 결과는 아래 원본에서 확인하며, 문서 작성 자체를 기술 역량이나 기능 완료의 증거로 삼지 않는다.

## 언제 무엇을 확인하는가

전체 계획을 세우거나 고칠 때, 다음 작업을 선택할 때, 제안한 범위·검증·일정이 적절한지 검토할 때 사용한다. 일반적인 GAS 개념 질문·로그 한 줄 설명·오탈자 수정에는 전체 절차를 요구하지 않는다. 작은 작업은 목적·확인 결과·다음 행동만으로 충분하다.

| 확인할 내용 | 유지할 원본 |
|---|---|
| 최신 요청, 실행·수정·커밋 허용 범위 | 사용자 지시와 [AGENTS](../../AGENTS.md) |
| 목적, 7단계 MVP, 포함/제외, 채택 게임 규칙 | [Project](../Project.md#mvp-scope) |
| 현재 작업, 남은 의존성, 일정과 첫 점검 시점 | [Roadmap](../Roadmap.md#next-work) |
| 실제 코드·책임·데이터 흐름 | 코드와 [Architecture](../Architecture.md) |
| 시험 조건·결과·미검증 | [Validation](../Validation/Index.md#active-tests) |
| 학습·판단·역할·계획 대비 차이 | [Development](../Development.md#daily) |

같은 정보의 원본을 새로 만들지 않는다. 문서와 실제 코드·로그가 다르면 차이를 밝히고 해당 범위부터 확인한다. 과거 성공을 현재 빌드의 통과로 넘기거나, 제안을 확정 규칙으로 바꾸지 않는다. 상태를 재확인하지 못했다면 확인 날짜와 한계를 남긴다.

## 무엇을 먼저 할지 판단하기

프로젝트는 작은 협동 게임의 완주와 전용 서버·GAS 기술 검증을 목표로 한다. AI 활용은 문제 정의·위임·판단·검증의 실제 사건으로 설명한다. 강의 수강과 운영 도구는 이 결과를 만드는 데 필요한 만큼 적용한다. 문서·자동화의 규모 때문에 플레이 구현과 검증이 계속 밀리는지도 점검한다.

후보가 여러 개라면 다음 질문으로 비교한다. 숫자 점수나 모든 후보의 장문 보고를 의무화하지 않는다.

| 판단 질문 | 선택에 반영할 내용 |
|---|---|
| MVP의 어느 결과에 필요한가? | 필수 동작·실패 처리·완주 가능성과 연결. 관련이 약하면 보류 이유를 적음 |
| 지금 가능한가? | 선행 기능·빌드·자산·기본 이해·시험 환경을 확인. 막힌 조건부터 해결 |
| 무엇을 아직 모르는가? | 서버 권한·중복 지급·취소·상태 수명처럼 결과를 깨뜨릴 미검증을 구체화 |
| 어떤 확인 가능한 결과를 남기는가? | 기능 변화, 선택 이유, 재현 가능한 시험. 코드량·문서량은 성과 지표로 쓰지 않음 |
| 얼마의 작업을 감당할 수 있는가? | 학습·구현·빌드 대기·재검증·기록을 포함한 예상과 첫 점검 시점. 실측이 없으면 추정이라고 표시 |

현재 가장 필요한 주 작업과 선택 이유를 먼저 제안하고, 비교가 필요한 대안만 채택/보류 이유·손실과 함께 적는다. 범용화·추가 콘텐츠보다 선행 조건과 핵심 실패를 우선하되, 기존 채택 범위를 조용히 축소하지 않는다.

일정이 밀리면 최초 기한·현재 결과·남은 의존성·새 예상의 근거를 함께 보여 준다. 시간이 부족하다는 이유로 통과 조건을 낮추거나 완료를 선언하지 않는다. 범위 축소, 검증된 기술 사례로 제출, 일정 조정은 선택지와 영향을 제안하고 채택 여부를 구분한다. 가용 시간 진술은 실제 생산 속도가 아니다.

<a id="execution"></a>
## 학습·구현·검증을 하나의 작업으로 묶기

착수할 때 기대 동작과 실패 조건을 먼저 정한다. 필요한 개념은 강의 노트·공식 자료에서 찾아 현재 코드에 연결한다. 강의 챕터는 학습 참조 단위이며, 구현 순서와 문서 분리는 기능의 의존성과 책임을 따른다. 프로젝트에는 강의 복사본 대신 적용 이유·차이·확인 결과를 남긴다.

| 단계 | 남길 결과 |
|---|---|
| 작업 정의 | 목표·포함/제외·완료 조건·첫 점검 시점 |
| 필요한 학습 | 부족한 개념, 읽을 자료, 프로젝트에서 달라지는 선택·시험 방법 |
| 구현 | 허용된 작은 동작과 관련 책임·수명·데이터 흐름 |
| 검증 | 채택 규칙에서 도출한 기대값, 실제 조건·결과·실패와 재검증 |
| 사용자 확인 | 핵심 코드 읽기·조건 변경·직접 조작 중 필요한 확인. 실제 수행과 대기를 구분 |
| 종료와 다음 | 추가 완료·미달·막힘·이월, 관련 문서 갱신, 다음 행동과 담당 |

AI는 허용 범위에서 조사·설계·구현·시험·기록을 수행한다. 사용자는 목표·중요 범위와 선택을 판단하고 핵심 동작·이해를 직접 확인한다. 일상적인 구현 선택마다 재승인을 요구하지 않으며, 사용자의 질문이나 AI의 시험을 본인의 이해·조작 완료로 기록하지 않는다.

전용 서버/GAS 검증은 실행 위치를 구분한다. 소유 클라이언트 입력, 서버 승인/거절, 상태 변경, 관찰 클라이언트 복제를 연결한다. 클라이언트 차단과 서버 거절, Editor와 독립 패키지, AI 실행과 사용자 재현은 별개의 확인이다. 서버 함수 직접 호출만으로 실제 클라이언트 요청을 검증했다고 하지 않는다.

공격은 비용·쿨다운·거리·대상·취소와 상태 정리를, 공용 상자는 동시 열람·남은 수량·개인 지급을, 적 전리품은 사망 시 생성과 팀 지급의 중복 방지를 검토한다. 적용할 조건·반복 수·판정은 [현행 시험 기준](../Validation/Index.md#active-tests)을 따른다. 모든 기능에 같은 시험 묶음을 강제하지 않는다.

## 검토 결과를 포트폴리오 근거로 연결하기

계획 검토에서는 목적 적합성·의존성·완료 조건·일정·역할을 확인한다. 구현 검토에서는 관련 코드와 실제 시험을 추가로 대조한다. 계획 검토만으로 코드 정확성이나 게임 시험 통과를 선언하지 않는다. 검토 결과 수정이 필요하지 않으면 유지 이유와 한계를 보고한다.

| 보여줄 능력 | 판단과 연결할 실제 근거 |
|---|---|
| 전용 서버·네트워크 | 실행·접속·소유권, 서버 판정과 복제, 종료·재시작·네트워크 조건의 확인 범위 |
| GAS | 입력·능력 수명·비용/쿨다운·GE·속성 복제, 거절/취소 후 재사용과 정리 |
| AI 리더십 | 위임한 목표와 제약, AI 수행, 본인의 실제 채택·수정·거절·후속 확인 |
| 구조화·학습 실행 | 문제 분해와 완료 조건, 부족한 이해에서 학습·적용으로 이어진 변화 |
| MVP 운영 | 최초 계획 대비 실제 결과, 미달 원인과 대응, 완주한 게임 범위 |

중요한 사건은 **책임 → 판단 → 성과**로 설명한다. 누가 실제로 무엇을 했는지, 왜 선택했는지, 어떤 조건에서 무엇을 얻었는지 연결한다. 비교하지 않은 대안·시간 절감·실패 사례를 만들어내지 않는다. 모든 작업에 세 역량이나 별도 사례 문서를 요구하지 않는다.

기능 설명은 기존 주제 문서에 누적한다. 비용·쿨다운·취소는 기존 GAS 문서의 관련 절을 보완하고, 공용 루팅처럼 독립된 책임은 실제 설명할 내용이 생겼을 때 새 문서로 나눈다. 현재 구조는 Architecture, 시험 상세는 Validation, 과정은 Development, 다음 행동은 Roadmap에 두고 연결한다.

공개 자료에는 플레이 결과, 대표 문제 해결, 구조·검증 근거, 본인/AI 기여와 한계를 추려 담는다. Markdown은 의미 있는 변경 때 갱신하고 HTML/PDF는 중간 목표 완료·공유 시점에 편집한다. 코드/시험 기준과 편집 판본을 맞추며 내부 대화·일지 전체를 공개 본문으로 옮기지 않는다.

## 사람과 에이전트가 사용하는 방법

사람은 작업 후보와 제약을 설명하고 이 문서를 기준으로 계획/제안/검토를 요청한다. 에이전트는 [cooprpg-work-planning](../../.agents/skills/cooprpg-work-planning/SKILL.md)을 적용해 실제 상태를 확인한다. 결과 문서 갱신은 [cooprpg-feature-docs](../../.agents/skills/cooprpg-feature-docs/SKILL.md)가 담당한다. 두 스킬에 같은 기준 본문을 복사하지 않는다.

다음은 요청 예시이며 지금 실행하라는 지시가 아니다.

> cooprpg-work-planning을 사용해 Roadmap과 실제 검증 결과를 기준으로 다음 작업 하나를 제안해줘. 필요한 학습·범위·완료 조건·역할·첫 점검 시점을 포함하고, 이번에는 구현하지 마.

> 이 작업 계획이 MVP 목적과 일정에 맞는지 검토해줘. 확인된 근거, 누락된 실패 조건, 유지·수정·보류할 항목을 구분해줘.

답변은 작업 규모에 맞춰 **현재 상태와 근거 → 선택과 이유 → 범위·완료 조건 → 학습·역할·시간 → 기록과 다음 행동**을 연결한다. 계획에는 아래 양식에서 필요한 항목만 사용한다. 단순 제안은 답변으로 충분하며 새 계획 파일을 매번 만들지 않는다. 채택된 현행 작업·의미 있는 결정은 기존 카드와 기록을 갱신한다.

```text
요청: 계획 / 다음 작업 제안 / 계획 검토
기준: 실제 저장소·브랜치·HEAD·미커밋 변경, 관련 코드/시험
현재 확인: 완료 / 부분 / 미실행 / 미확인
선택: 작업·MVP 연결·지금 하는 이유 / 필요한 대안과 손실
범위: 포함·제외 / 완료 조건·실패 조건
진행: 필요한 학습 / 사용자·AI 역할 / 예상과 첫 점검 시점
종료: 갱신할 문서 / 남은 확인 / 다음 행동
```

세션이 나뉘면 [인계 양식](../Development.md#handoff-template)에 버전·미커밋 변경·담당 파일·남은 시험을 남긴다. 같은 파일·에디터·빌드·포트는 담당을 정해 사용한다. 목표 모드·에이전트·새 세션의 사용은 요청 범위에 맞춰 제안하며, 계획 요청을 실행·커밋·게시 허가로 확대하지 않는다.

저장소 스킬은 작업 위치에 따라 발견 여부가 달라질 수 있다. 자동 선택이 되지 않거나 저장소 밖 채팅이면 실제 경로 `C:/CoopRPG/.agents/skills/cooprpg-work-planning/SKILL.md`를 읽도록 요청한다. 이 가이드와 스킬의 다른 장비·새 채팅 자동 로딩은 별도 확인 대상이다.

### 적용 예시 · V02 비용과 쿨다운

아래는 계획 방식의 예시다. 최신 진행 상태는 [현행 카드](../Roadmap.md#next-work)에서 다시 읽는다. 비용 부족·쿨다운 거절을 다음 범위로 잡았다면, 살아 있는 유효 표적과 부족한 자원을 따로 준비해 다른 거절 조건이 시험을 가리지 않도록 한다. 서버에 도달한 요청과 거절·최종값을 확인하고 사용자 직접 재현 범위를 정한다. 결과는 기존 GAS 문서에 누적하며, 새 게임 시험을 하지 않은 계획 단계에서는 성공으로 기록하지 않는다.
