# 검증 색인

작성일: 2026-10-29. 시험 절차·결과·증거의 진입점. 게임 규칙은 [Project](../Project.md), 작업 상태와 결정은 [Roadmap](../Roadmap.md)을 따른다.

## 문서 사용 기준

- **열람·수정 시점:** [AGENTS의 문서 책임](../../AGENTS.md#문서-책임과-종료-보고)을 따른다. 시험 실행자와 완료 주장을 확인하는 독자를 위한 기준·결과 색인이다.
- **포함·경계:** 시험 기준안·적용 범위·판정·증거 참조를 관리한다. 게임 규칙을 여기서 새로 확정하지 않으며 공통 환경은 Environment, 원시 자료는 Evidence에 둔다. 실제 실행 기록이 길어질 때만 별도 검증 기록으로 나누고 이 색인에서 연결한다.
- **최소 양식:** 기준은 기존 ID/대상/확인할 결과/현재 결과 표, 결과 색인은 기록/날짜·상태/한계와 필요한 증거 링크를 쓴다. 개별 게임 시험은 아래 `시험 기록과 증거` 양식을 사용하며 문서·읽기 조사는 날짜·방법·결과·한계만 기록한다.
- **검증:** 기대값이 채택한 규칙에 근거하는지, 조건과 절차를 재현할 수 있는지, 실제 결과·판정·증거의 빌드와 범위가 맞는지 확인한다. 미실행·부분 확인·실패를 전체 통과로 올리지 않는다. 기준의 문서 검토와 게임 시험 통과는 별개다.

## 검증환경 구성·도입 계획

CoopRPG / 2026-10-30. **목적:** 피처 브랜치의 변경을 재현 가능한 근거로 검토하고, 검증환경 자체의 결함·비용도 개선할 기준을 둔다. 사용자는 피처 단위 브랜치·검증·리뷰 후 머지하는 방향과 검증기·GitHub Actions 활용 의향을 밝혔다. 2026-10-30 후속 사용자 지시로 단계형 구성을 채택했다. 이번 허용은 기존 문서 커밋과 P1 구현·검증까지이며 P2 이후 실행은 보류한다. 채택을 구현·원격 설정 완료로 계산하지 않는다.

**현재 기준:** [환경 기록](Environment.md#ue-584-소스setup-준비-결과--2026-10-30)의 UE 5.8.4 소스·Setup 준비까지만 확인됐다. 게임 프로젝트·첫 빌드·게임 시험은 미착수다. 그 기록의 여유 공간은 당시 관측값이며 이번 계획 작성 시 재측정하지 않았다. 계획 작성 당시에는 문서만 갱신했다. 후속 P1 결과는 아래에 실제 수행 범위와 함께 추가하며, 워크플로·브랜치 보호·러너는 미구성이다.

읽는 순서: [구성](#권장-구성과-역할) → [판정](#검증기-판정과-근거) → [도입](#도입-순서와-완료-기준) → [운영·보완](#리뷰머지와-검증환경-보완). 게임 시험의 기대값은 아래 V01~V09와 Project를 원본으로 유지한다.

### 권장 구성과 역할

**권고:** 저장소가 관리하는 작은 검증 스크립트를 로컬과 Actions에서 함께 호출한다. Actions에는 실행·결과 게시를 두고 판정 로직을 복제하지 않는다. 자동 검증은 규칙·구현 오류 탐지, AI 리뷰는 설계·누락·전제 검토, 사람은 핵심 선택과 실제 조작·표현 확인을 맡는다. 셋의 결과를 서로 대체하지 않는다.

| 구성 | 장소·도구 제안 | 실행 시점·대상 | 근거·한계 |
|---|---|---|---|
| 저장소 검사 | `Tools/Validation/`의 PowerShell 7 스크립트, GitHub-hosted `windows-2022`·`pwsh` | 모든 PR: 내부 링크·앵커, Git 제외/LFS 속성, 금지된 생성물·대형 파일 혼입, 해당 설정 형식 검사 | 로컬 셸은 7.6.5 확인. CI의 실제 버전·호환성은 도입 때 확인·기록. 외부 URL 전수 접속은 PR 필수 검사에서 제외하고 필요할 때 실행 |
| 빌드·빠른 자동 시험 | DSYEOM, 고정 UE 소스와 기존 VS 도구, UBT/UAT·UE Automation Framework | 관련 C++/타깃/설정 변경: 영향받는 타깃 빌드·선택한 규칙/데이터 검사 | 첫 빌드 성공 후 명령 자동화. Editor만 성공한 결과로 Server/Game 빌드를 통과시키지 않음 |
| 독립 프로세스 통합 | 데스크탑 서버 1·클라이언트 2, 개발용 시험 맵/입력 경로. 반복 비용 확인 후 Gauntlet 검토 | 접속·GAS·복제 변경과 단계 종료: V01~V03부터 실제 요청→서버 처리→복제 관측 | PIE·서버 함수 직접 호출로 대체하지 않음. 무화면 시험은 렌더링·조작감 근거가 아님 |
| 실제 장비·사람 확인 | 노트북은 추후 별도 시험 클라이언트, LAN·수동 플레이 | 관련 피처의 조작 확인, 별도 PC·지연/손실·한 판 완주는 단계별 확대 | 두 번째 PC의 준비·접속·일정은 미검증. 동일 PC 자원 경쟁과 별도 PC 결과 구분 |

초기 CI는 엔진·게임 자산을 받지 않는 가벼운 검사로 시작한다. 향후 LFS 객체가 필요한 자산 검사는 객체 취득 여부를 명시하고, 포인터 검사와 실제 자산 검사를 구분한다. 검증 루트는 저장소에서 계산하고 로컬 엔진 경로는 명시 인자로 받으며 사용자 절대 경로·인증을 공용 스크립트에 고정하지 않는다. 초기 PowerShell 7 제안은 기존 Windows 환경을 활용하려는 판단이며 새 언어나 패키지 설치를 전제로 하지 않는다.

**대안 판단:** 표준 호스티드 러너에서 매 PR마다 UE 소스 전체를 취득·빌드하는 방식은 초기 점유·시간 비용 때문에 보류한다. 공개 CoopRPG에 개인 데스크탑을 상시 self-hosted runner로 연결하는 것도 권하지 않는다. 전용 격리 러너·별도 비공개 빌드 저장소·유료 러너는 실제 반복 비용이 병목이고 비용·접근 통제 선택이 필요할 때 비교한다. 비공개 저장소만으로 격리가 보장되지는 않는다. [호스티드 러너 사양](https://docs.github.com/en/actions/reference/runners/github-hosted-runners), [GitHub 보안 지침](https://docs.github.com/en/actions/reference/security/secure-use)

### 검증기 판정과 근거

- **적용 범위:** 작업 시작 시 문서/저장소, 빌드, 게임 통합 중 필요한 검사와 이유를 선택한다. 변경 파일 분류는 보조 수단이며 C++·Config·Content·시험 코드 변경을 문서 전용으로 분류하지 않는다. 애매하면 관련 검사를 추가한다. 아직 없는 Game 폴더를 요구해 문서 전용 검사를 실패시키지 않는다.
- **최소 출력:** 실행 ID·시각, 시험/검사 ID, 대상 HEAD·미커밋 여부, PR head/base 및 실제 검사한 커밋(해당 시), 검증기 버전, 엔진 SHA·도구·타깃(해당 시), 실행 명령·종료 코드, 예상/실행/실패 개수, 판정·근거 경로를 JSON과 짧은 사람이 읽는 요약으로 남기는 안이다. 정확한 스키마는 도입 단계에서 필요한 필드부터 구현한다.
- **실패 처리:** 필요한 실행 파일 부재, 선택한 시험 0개, 결과 파일 누락·파싱 실패, 프로세스 충돌·시간 초과, 예상한 사례 미실행은 통과가 아니다. 종료 코드 0뿐 아니라 실제 결과를 검사한다. 결과는 통과·실패·미실행을 유지하며, 적용 제외는 사유를 별도로 기록하고 게임 통과 개수에 넣지 않는다.
- **재현·수명:** 사례는 사전 상태를 명시하고 독립적으로 초기화한다. 세션마다 출력 경로를 구분하고 자신이 시작한 PID·포트·작업 폴더만 관리한다. 실패 때도 로그를 회수하고 프로세스 잔존을 확인한다. 다른 작업·영상·사용자 프로세스를 일괄 정리하지 않는다.
- **검증기 자체 확인:** 정상 자료와 의도적으로 깨진 링크·잘못된 설정·누락된 결과·0개 시험·시간 초과 등의 작은 표본으로 정상 통과와 실패 차단을 확인한다. 구현한 검사·실패 경로만 대상으로 하며, 미래 기능용 대형 테스트 플랫폼을 미리 만들지 않는다.
- **기대값 독립성:** 게임 기대값은 채택한 Project/V 기준에서 작성한다. 구현 함수의 결과를 그대로 기대값으로 계산하거나 별도 가짜 게임에서 통과한 것으로 실제 GAS·네트워크 성공을 주장하지 않는다.
- **보관:** 로컬 원시 자료는 향후 `Artifacts/Validation/<실행 ID>/`에 두고 Git에서 제외한다. PR/검증 기록에는 실행 ID·대상·판정·원시 근거 위치를 연결한다. 공개 Actions에는 검토된 최소 검사 로그만 보관하고 인증·엔진 소스·권한 미확인 자산·대형 패키지는 올리지 않는다. CI artifact 보존 기간은 초기 14일 제안이며 중요한 실패·릴리스 근거는 만료 전에 별도 보존한다. 자동 삭제는 별도 정책 없이 추가하지 않는다.

### 도입 순서와 완료 기준

아래 시간은 **제안한 작업 한도**이며 예상 성공 시간·개발 속도가 아니다. 한도에 도달하면 미완료 원인과 남은 일을 보고하고 축소·재계획한다. 엔진 첫 빌드 시간은 미실측이므로 이 한도에 끼워 맞추지 않는다.

| 순서·작업 단위 | 포함·완료 확인 | 시간 한도·의존성 제안 |
|---|---|---|
| P0 운영 기준 정리 | 기존 미커밋 Setup 기록과 계획 변경을 구분해 검토. 브랜치·PR의 완료 기준, 대상 SHA·증거·사람 확인의 최소 항목 확정. 게임 미실행 상태 보존 | 1시간. 구성 제안 채택·후속 실행 범위 확인 후 시작 |
| P1 로컬 저장소 검증기 | `chore/repository-validation` 예시 브랜치. 기존 문서 링크·Git 정책 등 필요한 검사부터 구현하고 정상/실패 표본으로 차단 확인. 로컬 단일 진입점·실행 요약 제공 | 4시간. UE·GitHub 인증 없이 실행 가능하게 시작 |
| P2 Actions·머지 차단 | `ci/repository-validation` 예시 브랜치. 동일 검증기를 PR에서 실행하고 정상·의도적 실패·문서 전용 변경·후속 수정의 체크 결과 확인. 실제 체크 성공 후 main 보호 설정 | 2시간. P1 완료와 원격 게시·워크플로 실행·설정 변경 허용 필요. 러너 등록·엔진 빌드 제외 |
| P3 첫 빌드·접속 기준 확보 | 별도 환경/기능 브랜치에서 고정 소스 Editor, 최소 게임 Server/Game·쿠킹·V01 실제 실행. 선택 도구·명령·소요·공간·로그 확인 후 성공한 절차를 검증기로 감쌈 | 프로젝트 생성·빌드 별도 허용 필요. 착수 때 첫 빌드 관찰 한도 결정. 실패 조사 기록도 남기되 기능 통과로 올리지 않음 |
| P4 피처별 자동 시험 확대 | V02·V03의 정상/거절/중복/취소 시험을 관련 기능과 함께 구현. 반복 프로세스 관리가 필요하면 Gauntlet 비교·선택. 별도 PC·지연/손실·회귀는 단계별 추가 | 각 피처 카드에 포함. 모든 V01~V09 자동화를 개발 착수의 선행 조건으로 요구하지 않음 |

빌드가 안정화되면 PR에서는 관련 타깃의 증분 빌드·선택 회귀를 우선한다. 타깃/의존성 변경, 누적 산출물 의심, 제출 후보에서는 깨끗한 프로젝트 산출물로 재현을 확인한다. 매 문서 PR마다 엔진 전체 clean 빌드를 수행하지 않으며, 엔진 소스 자체가 같다는 이유만으로 다른 게임 코드의 이전 결과를 재사용하지 않는다.

### 리뷰·머지와 검증환경 보완

**머지 제안:** main에서 작은 작업 브랜치 하나 → 범위·완료 기준 → 구현/검증 → PR → 작성 과정과 분리한 리뷰 → 중요 지적 수정·관련 재검증 → 사용자 판단 후 머지. 단독 작업에서는 develop·릴리스 브랜치·merge queue를 초기 필수로 두지 않는다. 사소한 문서 수정은 작은 PR로 처리하고 전체 설계 문서를 추가하지 않는다. 실제 브랜치·PR·머지 실행은 그 작업의 허용 범위를 따른다.

- **자동 차단 범위:** P2 초기 필수 체크는 예시 `repository-validation`이며 저장소 검사만 증명한다. PR 워크플로는 항상 시작하고 필요한 하위 검사들의 결과를 최종 작업에서 `always()`로 종합한다. 필수 검사의 실패·취소·필요한 실행 누락은 성공으로 바꾸지 않는다. 경로 필터로 워크플로 자체를 생략해 Pending을 만들지 않는다. 이름은 워크플로 간 유일하게 정하고 실제 실행 SHA와 병합 기준을 확인한다. [필수 체크 지침](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks)
- **사람이 확인할 범위:** 초기 로컬 UE 결과는 PR의 대상 커밋·빌드 ID·로그를 사람이 대조한다. JSON 형식 검사나 녹색 저장소 체크를 실제 로컬 실행의 독립 증명으로 올리지 않는다. 검증 뒤 게임 코드·의존성·조건이 바뀌면 영향받는 결과를 다시 확인한다. 제출용 결과는 clean 상태·명시한 빌드와 연결한다. 미커밋 실험은 개발용으로 구분한다.
- **보호·권한:** PR 경유·필수 체크·리뷰 대화 해결, main 강제 푸시/삭제 차단을 제안한다. 별도 권한 있는 리뷰어가 확보되기 전에는 승인 1개를 기계적으로 필수화하지 않는다. 작성자는 자기 PR을 승인할 수 없고 AI 검토 기록은 GitHub의 필수 승인과 다르다. [브랜치 보호](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches), [승인 제한](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/approving-a-pull-request-with-required-reviews)
- **워크플로 안전성:** 기본 `contents: read`, 불필요한 secrets 없음, 외부 Actions는 검토한 전체 커밋 SHA 고정, 잡 시간 제한·PR별 중복 실행 취소를 제안한다. 권한 있는 `pull_request_target`에서 PR 코드를 실행하지 않는다. 검증 코드·워크플로 자체 변경도 리뷰하며, 현재 초기 구성은 악의적인 저장소 쓰기 권한 보유자를 완전히 방어하는 체계가 아님을 인정한다.
- **보완 시점:** 첫 로컬/CI 결과 차이, 검증 누락으로 머지된 결함, 거짓 실패·간헐 실패, 엔진/도구·시험 기준 변경, 반복 시간이 병목일 때 관련 구성만 검토한다. 단계 종료 시 기존 피처 회고와 함께 미탐지·거짓 실패·수행 시간·수동 부담·보관 공간을 짧게 확인한다.
- **보완 기록:** 문제·영향 사례 → 원인/미확인 가설 → 변경한 검사·적용 범위 → 실패 표본과 재검증 → 남은 한계를 이 색인의 관련 절/결과에 연결한다. 중요한 해결만 Cases로 분리한다. 불안정 시험을 재실행해 녹색 결과만 남기지 않는다. 격리하면 이유·담당·복구 시점을 적고 해당 위험을 별도 확인하기 전까지 피처 완료 근거로 쓰지 않는다.

**문서 운용 판단:** 문서화는 필요하지만 설정을 복사한 장문의 매뉴얼과 작업마다 별도 보고서를 만드는 것은 권하지 않는다. 이 절은 목적·구조·판정·보완 원칙, Roadmap은 도입 상태·다음 일, Environment는 실측·실제로 검증된 명령, 개별 시험은 아래 시험 기록 양식을 맡는다. 구현 후 제안과 실제 구성을 맞추고, 규칙 변경 이유와 과거 실패 근거를 보존한다. 최신 명령은 실행 스크립트를 원본으로 삼고 문서에는 사용 조건·연결만 둔다.

**남은 선택·조사:** 초기 단계형 구성은 사용자 채택이고 현재 P1만 실행 허용됐다. 유료/전용 러너 비용이 필요해지면 그때 조율한다. 4주 기준일·주당 작업일은 기존 D04-S를 유지한다. CI의 실제 런타임·설정 가능 여부·첫 빌드 비용·Gauntlet 적용성·두 번째 PC 조건은 AI가 해당 착수 때 조사하며 지금 사용자에게 기술 정보 선택을 넘기지 않는다. ## 첫 기술 검증 범위와 통과 기준

**채택 상태:** 2026-10-30 D02-S 문서 정리 요청에 따른 AI의 기술 판단이다. 첫 검증의 범위·통과 기준을 선택한 것이며 게임 전체 MVP의 제안·최종 정원·밸런스를 확정한 것은 아니다. 현재 전부 미실행이며 설치·구현·빌드 허용도 포함하지 않는다.

**착수 조건:** 데스크탑의 실제 호스트·경로·도구·공간 조사, 엔진 구성 선택과 실행 허용을 먼저 마친다. 접속/입력 흐름(D09-S), GAS 수명(D05-S), 공격 판정·예측 범위(D06-S), 공격 비용·쿨다운·취소 시 환불 규칙(D07-S)은 해당 구현 전에 선택한다. 게임 규칙은 Project에, 실제 구조는 구현 시 Architecture에 반영한다. 각 선택은 현재 하위 작업에 필요한 만큼만 하고 후속 다운·부활·재시작 전체 설계를 접속 시험의 선행 조건으로 두지 않는다. 아래 고정 표적 값은 시험 전용 조건이며 실제 전투 밸런스와 구분한다. 필요한 소규모 기본 자산 외 스텔라 전체 이식을 선행 조건으로 두지 않는다.

| 순서·적용 범위 | 최소 실행·실패 경로 | 통과 기준 |
|---|---|---|
| 1. 빌드·접속 — V01 | 선택 소스로 Editor·게임 Server와 접속용 Game 또는 Client 타깃을 빌드하고 필요한 맵·실행 데이터를 쿠킹/준비. 동일 PC에서 에디터 없이 독립 서버 1개와 실제 클라이언트 프로세스 2개 접속, 각 창 입력으로 이동. 전체 종료 후 다시 시작·접속하는 과정을 1회 수행 | 빌드 성공과 실행물 연결 확인. 양쪽이 서로의 캐릭터 이동을 수신하고 각 입력은 자기 소유 Pawn에만 적용. 서버 종료가 클라이언트에서 감지되고 연결 종료 상태로 전환. 명시적으로 종료한 프로세스는 남지 않으며 재실행 후 다시 접속 가능. 연결 종료 안내는 로그로 확인할 수 있고 전용 UI는 필수 아님 |
| 2. GAS 단타·권한 — V02 | 실제 클라이언트 입력→능력 요청→서버 판정→두 클라이언트 관측. 정상 공격, 비용 부족·쿨다운 중 요청, 판정 범위 밖/무효 대상, 같은 공격의 동일 대상 중복 접촉을 구분 | 고정 표적 체력 100에서 피해 10의 승인 공격 3회 후 서버와 두 클라이언트의 최종 체력 70. 서버가 거절한 요청은 피해·부당한 비용 차감 없음. 판정 범위 밖/무효 대상은 피해 없음. 유효하게 발동했으나 빗나간 공격의 비용은 채택 규칙에 따름. 중복 접촉은 같은 공격에서 추가 피해 없음. 선택한 예측 범위의 거절 후 일시 상태·표현이 복구됨 |
| 3. 취소·수명 — V03 일부 | 서버가 피해를 확정하기 전에 취소를 수락하는 사례를 만들고, 거절/취소 뒤 조건을 회복해 재요청. 서버 승인 여부·취소/피해의 처리 순서·활성 능력과 상태를 기록 | 서버가 피해 확정 전에 취소를 수락했으면 피해 없음. 능력은 종료되고 해당 실행이 소유한 일시 Tag/Effect·콜백/타이머가 정리되어 영구 잠김·지연된 추가 피해 없음. 비용·쿨다운과 의도적으로 유지하는 Effect는 사전에 선택한 규칙과 일치. 조건 충족 후 새 공격이 정상 승인됨 |

클라이언트의 로컬 차단과 서버 거절은 구분해 기록한다. 서버 거절에는 실제 도달한 요청과 거절 이유의 증거가 필요하며 입력이 로컬에서 막힌 것만으로 통과시키지 않는다. 일반 조작으로 요청이 도달하지 않으면 개발용 최소 입력 경로·조건 조작을 통해 클라이언트에서 실제 요청 경로를 사용한다. 서버 검사를 우회하거나 별도 시험 프레임워크를 만들지 않는다. 서버 거절과 예측 상태 복구를 한 사례에서 관측할 수 없으면 사례를 나누고 한쪽 결과로 양쪽을 통과시키지 않는다. 취소는 서버 처리 순서로 판정하며 클라이언트가 먼저 취소를 표시했다는 이유만으로 이미 확정된 피해의 취소를 요구하지 않는다.

서버/클라이언트마다 빌드·프로세스·요청/공격 ID, 승인/거절·취소와 최종 상태를 연결할 증거를 남긴다. 서버 함수 직접 호출·AI Pawn·PIE만으로 위 실제 클라이언트 입력/독립 실행 시험을 대체하지 않는다. 두 클라이언트 모두 요청자가 되는 사례를 포함한다. 값 비교는 변화가 멈춘 뒤 서버 확정값과 수신값을 비교한다. 첫 시험에서도 관측 종료 시한·반복 횟수·허용 오차를 D12-S에서 미리 정하고 시험 조건에 기록하며, 미정이면 통과 판정을 보류한다. 이때 첫 로컬 시험에 필요한 조건만 정하고 V08의 지연/손실·장시간 반복 전체를 선행 요구하지 않는다. 임의로 오래 기다린 뒤 일치했다는 이유로 복제 실패를 통과시키지 않는다.

빌드 범위 근거: [Epic 타깃 안내](https://dev.epicgames.com/documentation/en-us/unreal-engine/unreal-engine-build-tool-target-reference)는 Game을 독립 실행 게임, Client를 서버 코드를 제외한 게임 타깃으로 구분한다. 첫 접속 검증은 독립 Server와 접속 가능한 Game으로 시작할 수 있으므로 별도 Client 타깃을 추가 빌드하는 것을 필수로 하지 않는다. 실제 선택·쿠킹·실행 명령은 환경 준비 후 검증해 Environment에 남긴다. 능력 종료 후에도 일부 Effect를 유지할 수 있다는 [GAS 개요](https://dev.epicgames.com/documentation/en-us/unreal-engine/understanding-the-unreal-engine-gameplay-ability-system)에 따라, 종료 정리 대상과 의도적 유지 상태를 구분한다.

첫 단계 완료는 위 세 범위의 실제 통과 근거가 모두 있을 때만 기록한다. 전체 V03 통과로 표기하지 않으며 실패하면 원인·수정·같은 조건의 재검증을 남긴다. 자원 경쟁이 있는 단일 PC 실행과 별도 PC 실행을 구분한다. 실제 다운/부활·적 AI·루팅·탈출·한 판 재시작·회피·고급 UI는 이 단계에서 제외한다. 별도 PC 접속과 지연/손실 조건 확대는 안정화 대상이지만 서버 권한·중복 피해·거절/취소 정리는 첫 단계부터 확인한다.

## 수치·시험 조건 — 고정 표적 외 미확정 제안

- 고정 표적: 위 첫 기술 검증에서 체력 100, 피해 10×3 후 70을 시험 조건으로 선택했다. 방어·추가 피해·자동 회복 없이 매 사례 초기화한다. V07의 데이터 변경 후 피해 15×3이면 55라는 조건은 아직 제안이다.
- 네트워크: 추가 지연 없음, 실측 RTT 약 100ms, RTT 150~200ms와 설정 경로 1~2% 손실. 설정값과 실측값, 적용 프로세스·송수신 방향을 구분한다.
- 반복: 주요 거절·취소·동시 획득 조건별 10회, 동일 루팅 요청 재전달 100회, 승리·패배·중단을 포함한 재시작 5회, 통합 실행 30분은 초기 후보다. 수량은 D12-S에서 비용 확인 후 선택하고 측정 가능성과 기준 충족 여부는 D12-H에서 검증한다.
- 상태 수렴: 지속 변화를 멈춘 조건에서 마지막 서버 확정 후 2초 내 일치가 후보. 동기화되지 않은 PC 시각을 단순 차감하지 않는다. 측정 방법을 먼저 정한다. 위치 보간·쿨다운 UI는 별도 기준이다.
- 개인 인벤토리 상세는 서버/소유자만 비교하고 비소유자에 노출되지 않는지도 확인한다. 복제 대상에 맞춰 기대값을 정한다.
- 오류 주입과 자연 발생 문제, 패킷 손실과 동일 애플리케이션 요청 재전달을 구분한다. 반복 횟수만으로 무결함을 주장하지 않는다.

## 시험 기록과 증거

실행 시 `시험 ID / 규칙 버전 / 코드·빌드 ID / 실행 ID·날짜 / 환경·프로세스 배치 / 사전 상태 / 기대 결과 / 입력 순서 / 실제 결과 / 반복·실패 횟수 / 판정 / 증거 위치 / 결함·후속 작업` 순서를 기본으로 기록한다.

이 양식은 게임 실행 시험용이다. 공통 환경·빌드·절차는 실행 묶음에서 한 번 기록하고 사례별로 참조한다. 문서 수정·읽기 조사는 방법·결과·한계만 남기며 해당 없는 필드를 채우지 않는다.

판정은 통과·실패·미실행으로 구분한다. 일부만 확인했으면 범위를 나누고 전체 통과로 올리지 않는다. 재검증은 원래 실패 기록을 보존하고 연결한다. 요구나 잘못된 기대값을 정당하게 변경할 때는 이유·결정 주체·적용 버전을 남기고 새 기준으로 재검증하며 이전 결과를 소급 변경하지 않는다. 빌드 ID는 실제 코드 상태와 연결하며 Git 미도입 상태를 임의 커밋 SHA로 표현하지 않는다.

증거가 생기면 `Docs/Evidence/<실행 ID>/` 또는 명시한 외부 보관 위치를 사용한다. 로그·트레이스·사진·영상에는 해당 빌드·조건·확인 범위를 연결한다. 추적·대형 원시 파일 보관은 [Roadmap의 Git/LFS 정책](../Roadmap.md#d02-s-폴더git스킬-전달-정책)을 따르고 증거 생성 시 실제 보관 위치를 명시한다. 그림만으로 서버 권한을 입증하거나 로그만으로 조작감을 입증하지 않는다.

AI는 반복 입력·실행·로그 비교를 도울 수 있다. 규칙을 복제한 별도 테스트 게임 대신 실제 게임 모듈을 쓰는 테스트 맵/입력 경로를 우선 검토한다. 직접 서버 함수 호출, 실제 클라이언트 요청, 수동 플레이를 별도 시험으로 기록한다. 사람의 UI·협동 완주 확인을 자동 시험 결과로 대체하지 않는다.

성능 측정은 하드웨어·빌드·적 수·구간을 고정하고 서버 시간과 클라이언트 프레임을 구분한다. 서버/클라이언트를 한 PC에 함께 실행하면 자원 경쟁을 기록한다. 실제 문제를 발견했을 때만 수정 전후 개선을 주장한다.
