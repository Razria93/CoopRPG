**세션 운영 제안.** 구현 담당은 기능 코드와 통합 상태를, 검증 담당은 독립된 게임 규칙에 따른 기대값·재현·실패 판정을, 문서 담당은 고정한 코드/시험 판본의 설명·도식·가독성을 맡는다. 검토 담당이 별도 AI 세션이라는 사실을 사람의 독립 검증으로 표현하지 않는다. 사용자는 목표·범위·중요 선택과 직접 조작/이해 확인을 맡되 모든 일상 기술 결정을 승인하는 병목을 만들지 않는다. 계획·일지·검증 요약 같은 공유 파일은 그 작업에서 정한 한 담당자가 통합한다.

**인계 양식 제안.** 기존 현행 카드에 작업 ID/목표, 실제 경로·브랜치·기준 커밋·미커밋 변경, 수정 담당·파일 범위, 관련 규칙/설계/시험 링크, 완료·실패·미실행, 다음 행동과 완료 조건을 둔다. 매번 별도 인계 파일을 만들지 않는다. 인계받는 세션은 시작 전에 작업 트리와 기준 판본을 확인하고, 기준 변경 시 영향받는 검증/문서만 재대조한다. 게시·커밋·머지는 기존 허용 경계를 유지한다.

## 매일 기록하고 팀에 전달하는 방법

작업 시작 때 오늘 기대 결과와 완료 조건 하나를 정한다. 의미 있는 결과가 바뀐 작업 턴에는 이 기록을 함께 갱신하고 하루 끝에 [일일 양식](#daily-template)으로 요약한다. 약10분의 일일 정리와 중요한 사례20~40분은 초기 제안이며 당일 총예산 안에 포함한다. 단순 대화·미관측 활동의 실적을 만들지 않는다.

- 계획대로 완료: 결과·근거·판정. 추가 완료: 이유·원목표 영향. 덜 된 것: 확인 원인/추정·남은 작업·이월.
- 학습 확인: 수강과 설명/직접 수정/실행을 구분. 검증: 규칙·빌드·시험/실행 ID와 실제 통과/실패/미실행.
- 변경: 원목표·원기한/현재 예상/실제 통과, 검토한 대안·선택·손실·후속 결과. 제외를 완료로 계산하지 않음.
- 협업: 담당·현재 막힘·다음 행동·다음 확인 시점과 필요한 도움. 새 팀원이 README→Roadmap→기록/시험 근거로 이동하도록 유지.
- 기여: 사람이 목표/검토/실행한 범위와 AI의 조사·작성·수정·시험을 구분. 절감률은 비교 실측 없으면 쓰지 않음.
- 운영 원본은 이 파일 한 곳이다. 세션 종료를 이유로 일지/인수인계 파일을 계속 추가하지 않고 상세 시험은 Validation에 연결한다.

작업의 선택·계획 검토는 [작업 판단 가이드](Planning/WorkingGuide.md)와 [계획 스킬](../.agents/skills/cooprpg-work-planning/SKILL.md)을 따른다. 아래 기준은 실제 기능 설명을 어디에 어떻게 갱신할지 다룬다.

## 기능 문서를 누적하는 기준

2026-11-15 채택. 문서의 주제는 강의 챕터·함수·작업 턴이 아니라 독자가 이해할 기능의 문제·책임·검증 경계로 정한다. [문서 색인](../README.md#document-editions)에서 기존 주제를 먼저 찾고 [기능 문서 스킬](../.agents/skills/cooprpg-feature-docs/SKILL.md)을 적용한다.

| 상황 | 갱신 방식 |
|---|---|
| 같은 기능의 조건·코드·시험이 바뀜 | 기존 절·흐름도·근거를 보완. GAS 비용·쿨다운·취소는 현재 GAS 문서에 누적 |
| 독립된 문제·데이터 책임·시험 경계가 생김 | 실제 설명할 내용이 확보됐을 때 새 주제 문서 작성. 공유 루팅·라운드 진행은 후보이며 빈 파일은 만들지 않음 |
| 중요한 실패·선택·학습 사건 | Development에 실제 역할·판단·결과 기록. 독립된 문제 해결 설명이 필요한 경우만 Cases로 분리 |
| 사소한 수정·단순 질의 | 영향받는 설명만 수정하거나 답변으로 종료. 새 문서·상세 사례·PDF를 강제하지 않음 |

착수 때 목적·완료 조건과 기존 문서를 확인하고, 의미 있는 변경·시험이 끝나면 해당 절을 갱신한다. 구조 원본은 Architecture, 시험 상세는 Validation, 이력은 Development에 두고 기능 문서는 독자가 이해할 설명과 핵심 근거를 연결한다. 현재 설명은 최신 상태로 고치되 과거 결정·시험은 날짜와 함께 보존한다. 문서가 길어졌다는 이유만으로 기계적으로 나누지 않고 독립된 읽기 목적이 생겼는지 판단한다.

공개 편집본은 중간 목표 완료·공유 요청 때 갱신한다. Markdown·PDF의 표현 방식은 달라도 코드·규칙·시험 사실은 일치해야 한다. 승인된 도식의 의도를 보존하며 수정 영향이 있으면 해당 매체도 재검토한다. 편집 원본·출력본·기준 코드/시험·검수 범위·공개 상태는 README 판본 색인 한 곳에서 관리한다. 확인되지 않은 PDF 생성 당시 커밋은 미확인으로 남긴다.

책임·판단·성과는 위 역량을 보여 주는 사례의 전개 순서다. 모든 기능에 세 역량을 채우지 않으며 실제 근거가 있는 사건을 고른다. 질문·수강·문서 작성은 학습 과정이고 직접 이해·응용 완료와 구분한다. 사용자 진술, AI의 제안/구현/시험, 사람의 조작과 승인도 구분한다. 에이전트 수·프롬프트 수·코드량·문서 수나 비교 없는 시간 절감을 성과로 쓰지 않는다. 대표 사례는 결과와 한계까지 연결하고 공개 자료에 민감한 원대화·개인 자료를 자동 포함하지 않는다.

실제 협업 책임·행동·상태는 [AI 협업 근거 색인](Portfolio/AICollaborationEvidence.md)에 한 사례 한 행으로 누적한다. 새 사람 확인은 원본 시험 기록과 같은 행에 반영하고 AI 자동 시험만으로 직접 확인 상태를 올리지 않는다.

<a id="collaboration-operation"></a>
## 세션 역할과 인계

실제 저장소 또는 명시한 worktree에서 시작하고 AGENTS → README/Project → Roadmap 현행 카드 → 관련 코드·검증 근거를 읽는다. 대화 이름이나 이전 완료 메시지는 파일·실행 근거를 대신하지 않는다. 세션이 바뀌어도 같은 카드와 기능 문서를 이어 쓰며 현재 카드의 담당·버전만 갱신한다.

| 역할 | 책임과 수정 범위 |
|---|---|
| 구현·통합 | 허용된 기능 구현·수정, 빌드/시험 자원 관리, 공유 Roadmap·Development·검증 요약 통합 |
| 검증·검토 | 채택 규칙에서 기대값 도출, 변경분·실패 경로·실제 근거 대조. 기본 읽기이며 지적을 통합 담당에게 전달 |
| 문서 편집 | 고정한 코드·시험 판본의 설명·도식·가독성, 배정된 기능 문서/편집본 수정. 기능 통과 판정을 임의 변경하지 않음 |
| 사용자 | 목표·중요 범위 선택, 직접 조작·이해 확인. 허용된 일상 기술 선택마다 재승인을 요구하지 않음 |

하위 에이전트는 사용자 또는 적용 규칙이 명시한 범위에서만 위임한다. 이번 운영 보완은 마지막 읽기 검토 1명만 허용한다. 이후 모든 기능의 상시 에이전트 실행 허가로 확대하지 않는다. 목표 모드도 명시 요청 후 검증 가능한 작업 단위로 설정하며 전체 MVP를 자동 실행하지 않는다. 목표·세션 생성·커밋·게시·머지의 허용은 서로 승계되지 않는다.

같은 파일·UE 자산·빌드 출력·시험 포트/프로세스는 동시에 수정/사용하지 않는다. 공유 파일은 카드에 정한 통합 담당 한 명이 반영한다. 병렬 작업이 필요하면 서로 다른 파일 범위와 기준을 지정하거나 worktree로 분리하되 엔진 경로·포트 같은 공유 자원도 확인한다. 원격/브랜치 작업은 AGENTS의 경계를 따른다.

<a id="handoff-template"></a>
### 현재 카드에 넣는 인계 양식

```text
작업 ID / 기능 주제·목표 / 포함·제외 / 완료 조건:
실제 저장소·worktree 경로 / 브랜치 / 기준 HEAD:
미커밋·미추적 변경: 파일 목록 + 필요한 diff/해시 또는 스냅샷 위치
담당 세션·역할 / 수정 파일 범위 / 공유 파일 통합 담당:
빌드·에디터·시험 프로세스 담당과 사용 중인 자원(해당 시):
채택 규칙·구현 문서·시험 기대값·실제 근거 링크:
완료 / 실패 / 미실행 / 사용자 확인 대기:
다음 행동 / 막힌 조건 / 첫 점검 시점:
인수 확인: 실제 Git 상태·기준 판본·권한·수정 범위를 대조한 결과
```

인계하는 쪽은 기존 변경과 자기 변경, 남은 시험을 표시한다. 인수하는 쪽은 수정 전에 HEAD·dirty 상태·근거를 확인해 카드와 다르면 원인을 좁힌다. 기준이 바뀐 경우 영향받는 설명·검증만 다시 대조하고 오래된 성공을 새 상태의 통과로 승계하지 않는다. 막힘·사용자 답변 대기·시간 한도에 도달하면 확인 사실과 다음 선택을 보고하며 완료로 표시하지 않는다. 검토자는 지적의 근거·영향·요청을 반환하고 통합 담당이 수정·재검토 또는 보류 이유를 남긴다.

## 자동화의 조건과 보류

기존 저장소 검사·PR 절차를 유지한다. 수동 V01 성공 후 검증된 Server/클라이언트 명령을 실행 ID·빌드 ID·자신이 시작한 PID·타임아웃·로그 수집과 묶는다. 이후 반복이 실제로 생기면 특정 시험 요약·누락 검사를 추가한다. 시험0건/비정상 종료를 성공으로 세지 않고 실제 게임 모듈의 클라이언트 요청을 사용한다. 자동 도구가 본인의 설명·기여·완료 판단을 생성하지 않게 한다.

현행 확인(2026-11-15): [V01 자동 반복](Validation/Index.md#v01-server-shutdown)과 [V02 입력·로그 판정](Validation/Index.md#v02-log-context) 근거가 있다. 아래의 “이번 문서 보완에서 미제작”은 11월 5일 운영 보완 범위이며 이후 자동 실행 결과를 부정하지 않는다. 대형 대시보드·상시 예약·전체 Gauntlet/클라우드 인프라는 현재 보류다. 반복 비용/오류를 관찰했을 때 도입 비용과 비교해 재검토한다. 게임 자동화는 이번 문서 보완에서 제작·실행하지 않았다.

### 대표 판단 사례 선택

원인을 확인하고 실제 행동을 바꿨으며, 변경 뒤 결과를 확인한 사례를 우선 선택합니다. 사례는 1~2개면 충분하며 의미 있는 변경이 없다면 억지로 채우지 않습니다.

학습 지연으로 기능 구현 순서를 바꾼 경우, 서버 문제 때문에 콘텐츠를 줄인 경우, 검증 실패로 제출 범위를 바꾼 경우는 후보 유형입니다. 아직 실제로 발생한 사건이라는 뜻은 아닙니다.

각 사례는 아래 순서로 편집합니다.

1. 어느 목표에서 어떤 문제가 드러났는지와 당시 근거.
2. 실제로 검토한 대응과 선택 이유.
3. 유지한 핵심, 포기한 가치, 바뀐 기한·완료 조건.
4. 본인이 한 판단·직접 수정·검증과 AI가 지원한 범위.
5. 조치 후 확인한 결과와 남은 한계.

“단순화해서 시간을 절약했다”는 문장에는 무엇을 줄였고 실제 결과가 어땠는지 붙입니다. 비교 측정이 없다면 절약 시간을 수치로 쓰지 않습니다.
