# 프로젝트 기준

작성일: 2026-10-29. 목적·범위·게임 규칙의 원본. 현재 상태와 남은 확인/선택/검증 사항은 [Roadmap](Roadmap.md), 검증 결과는 [Validation](Validation/Index.md)에서 관리한다.

## 문서 사용 기준

- **열람·수정 시점:** [AGENTS의 문서 책임](../AGENTS.md#문서-책임과-종료-보고)을 따른다. 범위·설계·시험 기대값을 정하는 사람이 참조한다.
- **포함·경계:** 목적, 사용자 조건, 포함/제외 범위, 게임 규칙, 비교·성과 표현 기준을 관리한다. 진행 상태·설계의 코드 설명·시험 결과를 복제하지 않는다.
- **최소 양식:** 항목마다 상태 구분과 내용을 명시하고, 규칙에는 적용 조건과 기대 동작을 쓴다. 채택·변경 근거는 Roadmap의 관련 결정으로 연결하며 미결정은 해당 ID를 참조한다.
- **검증:** 다섯 목적의 누락, 포함/제외 범위와 규칙의 충돌, 제안의 무단 확정, 사용자 진술의 실측 사실화를 확인한다. 채택할 규칙은 시험 기대값으로 판정 가능해야 하며 수치·경합 순서가 미정이면 미정으로 남긴다.

## 1. 상태 구분

| 표기 | 의미 |
|---|---|
| 확정 요구 | 사용자가 정한 목적·제약 또는 채택한 운영 체계 |
| 제안 | 아직 개별 결정되지 않은 게임 규칙·구조·일정·수치 |
| 미결정 | 아직 선택하지 않은 사항. Roadmap의 ‘선택할 사항’에서 담당·시점·방법 관리 |
| 확인 사실 | 도구·파일·실행으로 확인한 결과. 날짜·방법·범위 명시 |

사용자 진술은 별도로 출처를 표시한다. 실측 결과와 혼동하지 않는다. 계획·문서 작성·코드 존재는 기능 통과의 근거가 아니다.

남은 일의 분류는 별도로 구분한다. **미확인 사실**은 자료·환경 조사로 확인할 정보, **선택할 사항**은 비교 근거로 채택할 결정, **검증할 가설**은 실행·측정으로 판단할 주장이다. 가설이 있다고 실행이 허용된 것은 아니며, 사실 확인이나 선택 완료만으로 가설이 검증되지는 않는다. 세 분류는 [Roadmap](Roadmap.md#남은-확인선택검증-사항)에서 관리한다.

## 2. 확정 요구

1. **기술 역량:** GAS와 데디케이트 서버 구현 경험을 실제 협동 액션 RPG·파밍·탈출 콘텐츠로 입증한다. 서버 경험은 UE 서버 타깃 빌드·실행·접속·서버 권한 게임플레이의 범위로 설명한다.
2. **다음 단계의 포트폴리오:** GAS를 의도적으로 사용하지 않은 스텔라의 자체 전투 구조 경험을 토대로, 같은 문제를 GAS에서 어떻게 해결하는지 비교한다. 단순 병렬 프로젝트가 아니라 언리얼 활용 역량 확장이 목적이다.
3. **AI 활용:** 콘텐츠 제작에서 작업 정의·맥락 제공·구현·검토·수정·검증을 체계적으로 수행하고 본인의 판단과 AI 기여를 구분한다. 업계 사례를 참고하되 채용 전체의 보편 기준으로 과장하지 않는다.
4. **문서화:** 목적·계획, 구조·구현, 문제 해결, 검증, 증거를 필요한 만큼만 기록한다. AGENTS와 최소 문서 체계를 사용하며 중복 인수인계 문서를 늘리지 않는다.
5. **MVP 통제:** 4주 목표 안에서 작은 실행 단위로 작업하고 포함·제외 범위와 완료 기준을 지킨다. 4주는 검증된 견적이나 확정 완료 보장이 아니다.
6. **작업 위치·현재 제약:** 루트는 `C:\CoopRPG`다. 현재 허용 작업과 임시 자료 보존 규칙은 [AGENTS](../AGENTS.md)를 따른다.

핵심 결과는 작은 게임의 완주와 기술 검증이다. AI 운영 체계·문서·자동화가 별도 대형 산출물이 되어 콘텐츠 완성을 밀어내지 않게 한다.

## 3. 사용자 제공 조건

2026-10-29 사용자 진술: 전체 작업 하루 약 12시간 중 병행하되 본 프로젝트에 최소 6시간 이상을 투입할 예정. GAS는 처음이며 스텔라에서 자체 구조를 구현한 경험이 있다. PC 2대 이상·시험 참여자를 확보할 수 있고 데스크탑/노트북의 LAN 구성이 가능하나 실제 연결 경험은 없다. 시험은 가능한 AI와 테스트 환경을 활용하기를 원한다.

위 내용은 가용 조건·선호다. 실제 작업 속도·LAN 접속 성공·자산 사용 권한의 증거는 아니다.

## 4. MVP 범위 — 제안

흐름: **준비 → 전투·상자 탐색 → 팀 목표 달성 → 탈출 → 결과 → 재시작**.

| 영역 | 최소 제안 | 의도 |
|---|---|---|
| 실행 | Windows 독립 서버 1개·클라이언트 2개 | 소유권·권한·복제 검증 |
| 공간·자산 | 작은 고정 맵, 공통 캐릭터·근접 무기 각 1종 | 콘텐츠 제작 부담 제한 |
| 전투 | 단타·체력·스태미나·재사용 제한, 근접 적 1종 | GAS 실행·거절·취소와 서버 피해 |
| 협동 | 다운·팀원 부활 | 상태 전이·완료/취소·참조 수명 |
| 파밍 | 공동 상자·개인 보유량·팀 점수 | 요청 검증·동시 획득·중복 방지 |
| 종료 | 탈출·승리/패배/중단·재시작 | 한 판 완주·상태 초기화 |
| 표현 | 필수 상태·결과·연결 오류 안내 | 실제 조작·관찰 가능 |
| 회피 | 조건부 포함, 초기 필수 작업에서 보류 | 이동 예측 비용 확인 후 판단 |

상자 수·전리품 종류·플레이 시간·부활/탈출 시간·피해량은 미확정이다. 콘텐츠 수는 처음부터 작게 시작한다. 기존 임시 문서의 3개 상자·2종 전리품·5~8분 등 수치를 요구로 계승하지 않는다.

제외 제안: 콤보·패링·락온·보스·추가 직업·무기 교체, 랜덤 맵·복잡한 인벤토리·제작·거래, 영구 저장·계정·DB·매칭·재접속 복구, PvP·대규모 접속·범용 롤백·클라우드 자동 배포.

## 5. 최소 게임 규칙 — 제안

- 서버가 최종 피해·아이템·라운드 결과를 확정한다. 입력 금지는 UI뿐 아니라 서버에서도 검사한다.
- 체력 0은 다운, 두 명 모두 다운되면 패배. 부활은 일정 시간 유지하며 이동·피격·다운·이탈·거리 초과·대상 변경 시 취소하는 안이다. 세부 허용 행동과 수치는 구현 전 확정한다.
- 공동 상자는 마지막 아이템에 두 요청이 들어와도 총 지급량이 잔여량을 넘지 않는다. 요청자·거리·상태·ID·수량을 검사하고 동일 요청 재전달과 이전 판 요청을 구분한다.
- 팀 점수 목표를 충족하고 두 명 모두 다운되지 않은 상태로 탈출 구역에 머무르면 성공하는 안이다. 이탈·다운은 진행 초기화, 피격만으로는 취소하지 않는 안이다.
- 종료는 한 번만 확정하고 추가 전투·획득을 차단한다. 재시작은 빈 보유량·초기 전투 상태로 시작한다.
- 준비된 두 명이 있어야 시작하며 진행 중 신규 참가·정원 초과를 거절한다. 진행 중 이탈은 판 중단, 서버 종료는 안내한다. 준비 상태의 재접속은 이전 상태 복구를 뜻하지 않는다.
- 획득 가능 총점은 목표 이상이어야 한다. 적 드롭은 초기 범위에서 제외하는 안이다.
- 탈출/다운, 획득/종료, 부활 완료/취소의 처리 순서는 미결정이다. 관련 기능 구현 전에 기대 결과를 정한다.

## 6. 스텔라 비교와 재사용 방향 — 제안

비교 축은 실행 조건·취소·정리, 자원·상태, 권한·예측·복제다. 각 축에서 이전 자체 구현, GAS 제공 기능, 여전히 직접 책임지는 코드, 선택의 장점·제약을 설명한다. GAS를 썼다는 사실만으로 품질·생산성 향상을 주장하지 않는다.

기존 구현 근거가 없는 기능은 일대일 비교를 만들지 않고 이번에 새로 습득한 범위로 표시한다. 과거에 같은 기능을 구현했다고 소급하지 않는다.

기존 규칙·종료 불변 조건·결함 사례·검증 방법을 우선 참고한다. 전체 프레임워크 자동 이식은 하지 않는다. 원본 자산과 프로젝트 전용 Notify·컴포넌트 의존성을 구분해 최소 자산만 선별한다. 재사용 가능성은 [환경 기록](Validation/Environment.md)의 검토 범위와 제한을 따른다.

## 7. 문서와 AI 성과의 표현

사람의 요구 정의·설계 판단·검토·실행 확인과 AI의 분석·구현·시험을 작업 기록에 구분한다. 중요한 사례가 생기면 `Cases`에 문제→원인→판단→수정→재검증을 남긴다. 전 대화·프롬프트를 수동 복제하거나 모든 함수의 설명서를 만들지 않는다.

사례에는 사용한 AI 도구(모델은 확인 가능한 경우), 맡긴 범위, 사람의 판단, 실제 검증 근거를 연결한다. 검토나 문제 해결을 AI가 수행했다면 그대로 기록한다. 생산성 수치 없이도 요구를 검증 가능한 결과로 연결한 과정은 설명할 수 있다. 다섯 목적의 최종 확인 기준은 [검증 색인](Validation/Index.md)의 목적별 근거를 따른다.
